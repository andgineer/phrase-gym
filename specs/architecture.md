# Small personal application

## Application boundary

Phrase Gym is a lightweight local Python service serving the retained Vue frontend and an HTTP API, with SQLite and local audio storage. The browser is the GUI. Use the normal browser on the learner's MacBook; no Qt, native Coach window or Electron bundle is required. A launcher can open the browser later if starting the application proves inconvenient.

Retain the original Vue visual and interaction design while replacing backend workflows. The compact header, warm page, centered practice card, serif phrase heading, prominent microphone control and responsive spacing are established interface choices. Show only controls supported by the current Python API; later practice and library workflows can return within this interface when implemented.

The Python server must work on both macOS and Linux. The MVP media player and recording experience target browsers on macOS; Linux browser audio support is deferred until after the MVP. Server portability does not expand the local-only access boundary.

Phrase Gym owns phrases, practice, scheduling, settings, recordings, the durable preparation request state and publication of ready content. A separately runnable, headless Python Coach owns reference synthesis, later agentic CLI calls and their heavier dependencies; it needs no special GUI. Phrase Gym owns the only user interface. Server startup must not depend on Piper, a model runtime or a preparation CLI subprocess. Already prepared practice remains available while Coach is stopped.

Python is chosen for straightforward local iteration and the Coach's speech/model integration. Use ordinary libraries for Phrase Gym's HTTP validation and scheduling and for Coach's speech work rather than maintaining ports of their internals. Keep the Phrase Gym service small even when Coach has large dependencies.

## Package and commands

Ship one `phrase-gym` Python distribution from one `pyproject.toml` and `uv.lock`. Keep all Python application source under `src/phrase_gym/server/`, `src/phrase_gym/coach/` and `src/phrase_gym/deploy/`. Put server HTTP adapters under `server/api/`; keep command parsing and dispatch small in `server/main.py`. Server flags, such as port, override configuration. Each module has one focused responsibility and follows the repository size boundary.

Core dependencies support the server alone. Piper runs in Coach's separately pinned private environment; the optional `coach` extra can supply later model preparation dependencies; the optional `deploy` extra supplies future cloud provisioning dependencies. The same wheel contains all three source areas, even in a lean installation. `uv tool install phrase-gym` installs the server; `uv tool install 'phrase-gym[coach,deploy]'` installs the full set. Installing only the `coach` extra is also supported. Server startup and CLI help must work with core dependencies alone; server runtime code must not depend on Coach or cloud packages. One installed environment is sufficient for the separate server and Coach processes; no second Coach distribution, environment or automatic dependency installer is required.

The intended user commands are `phrase-gym run` for the server, `phrase-gym coach` for foreground preparation, `phrase-gym install-coach` to register and start a per-user background Coach service, `phrase-gym uninstall-coach` to remove that registration while preserving application data, and `phrase-gym deploy` for a future configured cloud server. These commands describe the target interface, not current availability. `deploy/` owns local service registration and future cloud deployment, while Coach owns its runtime and the server owns practice and publication. Local service registration must not require the cloud `deploy` extra. The later service implementation targets macOS per-user launchd and Linux systemd user services. It does not move Coach into the server process or bypass the API-only handoff.

The distribution includes the built Vue client and required application resources. Installed user commands need no source clone, Node or Invoke. Invoke remains the repository's development, build, test and release entry point and may wrap packaged user operations. Keep the current documented development and installation commands accurate until the corresponding packaged commands are implemented.

## Responsibilities

Keep HTTP adapters, content validation/import, practice policy and persistence focused in Phrase Gym; put synthesis and later bounded AI execution in Coach. Vue renders state and owns browser audio effects. A pure practice reducer and focused route, preferences and audio adapters keep orchestration out of the main view. The current-view completion workflow owns the atomic phrase/FSRS and `practice_log` write; selection, publication and library reads remain separate responsibilities. HTTP adapters do not open hidden writes. Generate client API types from Phrase Gym's Python contract. There is no need to preserve every prototype endpoint or module boundary.

All preparation submissions, whether an external agent's package or text typed into the browser's Coach field, enter through the Phrase Gym API. The browser submits, never polls preparation and never contacts Coach; failure notices reach it inside the practice facts it already loads. Complete external-agent submissions include all reference audio and are validated and published atomically for immediate practice. Text-only preparation requests are persisted in SQLite before acknowledgement, even when Coach is offline. Coach retrieves pending work and submits results only through that API; it never reads or writes the application database directly. Phrase Gym validates results and publishes the entire ready batch, including references, in one transaction. Stable request/result IDs make retries idempotent across restarts and lost responses. Coach claims an interrupted item again; a failed item keeps its material and reason, and resubmitting the same material requeues it. Unrelated ready practice continues meanwhile. Use the smallest database-backed handoff that provides these guarantees; no broker, general distributed worker framework or high-availability protocol is required.

Use one application database and data directory outside the model's workspace. Keep submitted work, original reference audio and learner takes with their phrase association and recorded cue/help snapshots. Ordinary SQLite transactions make batch publication and a rated phrase/`practice_log` update coherent. Retrying a completed submission or grade must not duplicate phrases or practice completions. Phrase Gym remains the database writer; do not construct a general event platform.

Record the prompt, answer and support with each saved take so later edits cannot misdescribe playback. A replacement meaning starts a new phrase. Simple take snapshots suffice; immutable profile registries, publication generations, cross-target dependency graphs and versioned job capabilities are not required.

## Database access

SQL is hand-written against SQLite, without an ORM, query builder or added dependency. Each workflow's transaction takes SQLite's write lock up front, and the queries rely on SQLite's own date comparison, JSON functions, replace-on-insert and backup copy. The application is fixed to SQLite, so database portability buys nothing.

Rows that are read whole or passed between functions are typed records whose fields equal the query's columns. A query returning a column the record lacks, or lacking one it has, fails instead of silently dropping data, and the type checker rejects a misspelled column before commit. A test compares each whole-table record with a freshly created database, so a new upgrade step that changes one of those tables fails the tests until its record matches. Records keep stored values in their stored form: JSON stays text and flags stay integers until the code that uses them decodes them. A read that names a few columns and uses them beside its own SQL text stays a plain row.

A SQLAlchemy 2.1 proof of concept against this codebase (November 2026) found no reason to adopt an ORM:

- The SQL surface is small: 89 SQL calls in 3,160 lines of server code over 13 tables, four upgrade steps and a 61-line upgrade runner, with five runtime dependencies. SQL text is assembled only from fixed fragments (the search, lesson and date filters, the cue-or-hint column name, the shared schedule column list and the phrase insert), and every value is passed as a parameter.
- The actual weakness was 155 column names read as strings, which the type checker cannot see; it flags the same typo on an ORM class. Tests against a real SQLite file caught such typos. Typed records close this gap for rows read whole or passed between functions, without a dependency.
- By default the ORM lost updates: two writers read the same phrase and the second save silently overwrote the first. Restoring the up-front write lock took about ten lines of connection hooks, and a first attempt left the database locked.
- The ported rating save issued four statements where the current code issues two. The ported search took 24 lines against about 15, and table declarations took 59 lines for 3 of the 13 tables while duplicating the schema upgrade steps.
- It added about 10 MB installed (1.3 MB more if its migration tool replaced the upgrade runner) and about 0.1 s at start-up (93–124 ms warm import against 2–3 ms).

## Deletion cleanup

Phrase deletion removes visible records and invalidates the phrase's active view in one SQLite transaction. That same transaction durably records the owned reference/take paths awaiting deletion before their records disappear. Filesystem removal follows the commit; SQLite and filesystem changes are not claimed to be atomic. Paths remain pending until removal succeeds, with an already absent file treated as success.

Retry pending cleanup on server startup and through an explicit retry when cleanup fails. Expose the outstanding cleanup and actionable error until it succeeds, including after restart; do not report complete file removal early or restore a deleted phrase. Retry only recorded owned paths, and never reuse those paths for a replacement phrase or take. A small pending-path record suffices; no general job framework is needed. Late uploads still fail for the deleted phrase and cannot publish an orphan recording.

## Growth after the MVP

Preserve stable phrase/source and take identities, recorded support and independent audio references. Keep scheduling policy separate from activity presentation and recording storage. [Extra practice](decision-transfer-and-engagement.md) uses the same phrase and current-session rules as Daily; it does not need a second phrase identity or general activity engine. `Phrase` is one stored record with `text` as its wording; Card is only a Vue view. The planned phrase loop uses one completed-practice log and one mutable current-view record, with no separate historical attempt or review tables or duplicate daily aggregate counters. Two date-keyed values store Extra allowance targets; live settings and indexed log counts determine remaining capacity.

Implement only the first MVP's records and APIs now; no placeholder dialogue tables, generic workflow engine, plugin framework or speculative API endpoints are needed. Every stage keeps the learner's existing database under the [data compatibility rule](#releases-and-data-compatibility). Import packages use the current format only; older package formats are rejected rather than converted.

## Local access and privacy

For the first versions, Phrase Gym and Coach run on the same machine. Listen on loopback and serve Vue and the API from the same origin. Retain basic Host/Origin checks against unrelated websites. There are no accounts, application credentials, synchronization or public endpoints in the MVP. The learner has authorized private iPhone access through Tailscale Serve. Keep the backend on loopback and opt in to one exact HTTPS machine origin; Tailscale controls which tailnet devices may reach the shared library. Do not use Funnel or a public listener. This adds private access, not per-user data separation or automatic iPhone audio qualification.

The planned later placement runs Phrase Gym on a cloud host and Coach on the learner's laptop. The API-only handoff permits that placement without sharing the database or moving Piper/model dependencies into Phrase Gym. Remote access, authentication and deployment details must be designed before implementation, and deployment still requires the learner's explicit request. The current loopback/Tailscale setup does not implement it.

External course extraction happens outside the app. Imported source links are attribution, never instructions to fetch or execute anything. Model preparation payloads contain only submitted material and relevant language choices, never learner recordings, application-store contents, secrets or repository .env files. Coach uses its approved local login for CLI work but accesses Phrase Gym data only through the API. Published practice works while Coach is offline as long as Phrase Gym is running.

Coach runs Codex as the learner's selected subscription CLI with the normal user home, so the learner's own Codex login, model choice and settings apply. Its working directory is the Phrase Gym source checkout when Coach runs from one; an installed Coach without a checkout uses its own private cache directory. Coach keeps each attempt's private files under `.phrase-gym-coach/` there. The CLI's own sandbox, not prompt wording, bounds what model-run commands can do: they may read only system essentials and the current attempt's files; `.env` files, the rest of the working directory and the home directory, including the default application data directory, stay unreadable, and they write nothing and reach no network. The child process receives an allowlisted environment without provider API keys, so only the subscription login is used. Every call has a time limit and output caps; a quota or login failure ends that item with its reason instead of retrying.

## Backup and restore

Even for later personal production use, backup and restore are maintenance operations while the app is stopped. Stop Coach work, wait for pending browser saves, close Phrase Gym cleanly, then copy the entire data directory to a dated backup. This includes the database with pending preparation requests, reference audio, every saved take and settings. Never copy just a live SQLite main file while ignoring its journal.

Restore with the application stopped: keep the current directory as a fallback, copy back the whole backup and start the compatible application version. Check phrase counts, current due dates, daily statistics and representative reference/take playback. A manual documented procedure is enough for the first MVP; a later convenience command may automate these same steps.

No live restore, concurrent-backup protocol, lease invalidation, distributed snapshots, recovery service or high-availability machinery is required. A failed copy must not destroy the original. Backups are private learner data.

## Releases and data compatibility

Reuse useful Python code from Git and useful behavior/tests from both prototypes. Retain the Vue audio implementation and its real-device findings. Do not translate the Rust backend feature for feature or maintain two shipping backends. Change Vue and the new API together where that makes the reduced product simpler.

Prototype compatibility is not an MVP feature. Do not delete existing learner data or recordings during replacement. Use a clearly identified new application data directory; any later import of selected prototype content is an explicit, bounded action. Starting fresh does not authorize erasing old data.

The learner's practice history, schedules and recordings are real study data, so the application database is preserved from now on: no stage, schema change, demo or test run clears or recreates it. Every schema change ships with an upgrade that carries an existing database forward in place with all its data. Upgrades are numbered SQL steps shipped with the server and applied automatically at startup, before anything is served: the server first copies the database to a dated backup file beside it, then applies every missing step and records the new version in one transaction, so a failed step leaves the database at its old version. A new database is built from the same steps, giving the schema one definition. A step never changes once a learner database may have applied it; a correction is a new step. Version 5, the schema in use when this rule began, is the oldest database that upgrades. Phrase Gym uses plain SQL with no object models, so a migration library's model comparison and downgrade scripts add dependencies without benefit; the automatic backup provides the way back. Unknown, older or newer schemas fail with an actionable message and leave the data unchanged. Settings are one JSON document in the database rather than a column per setting, so adding or retiring a setting needs no upgrade step: a missing setting reads as its default, an unknown stored one is ignored, and the next save rewrites the document. Rollback uses the previous application version and its complete backup; it needs no concurrent operation support.
