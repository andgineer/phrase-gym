# Phrase Gym Coach, inbox and reference speech

## Ownership boundary

Phrase Gym Coach is a Rust desktop GUI application for Windows and macOS. It processes the inbox through an API hosted by [Phrase Gym Server](architecture.md), backed by the same database as learning. The server hosts that API and stores all durable inbox entries, personal preferences, jobs and delivery receipts alongside learning data. Coach claims work and persists changes through the API; it has no separate authoritative database and never opens the core SQLite file over a network. The core validates packages and publishes content atomically; it never launches a preparation agent or speech provider. Published practice, inbox submission and preference updates continue when Coach is offline.

Website import is outside Coach and the inbox. The learner uses an external agent to visit sources, handle access, extract text and audio, and submit the resulting material through the inbox API. The inbox neither opens URLs nor manages browsers, source logins, page parsers or source-specific extraction instructions. Source URLs may be retained as opaque provenance, never as fetch requests. A URL-only drop is rejected with an explanation to submit extracted material instead. External source workflows remain read-only unless separately authorized.

There is no routine human approval before prepared cards enter practice. Accepted preparation workflows require representative semantic assessment before unattended use; structural validation alone cannot establish language quality. The learner can suspend and recreate bad cards during practice.

## Desktop application

V1 contains only an inbox drop area, settings selecting Codex or Claude CLI, and basic processing status/database counts. Detailed GUI design and queue browsing, job-detail screens, charts and diagnostics dashboards are deferred. A deliberate paste/drop automatically initiates validation, preparation, transfer and atomic publication through the inbox API; a demo button may emulate that input. There is no separate Connect or Send action, file-path setup or manual pipeline step in ordinary intake. The local demo connects Server and Coach directly on the same MacBook using their shared loopback default, with no application authentication or credential setup; remote operation and social sign-in are deferred under the [access boundary](architecture.md#private-release-and-recovery). Opening or closing an input surface alone submits nothing. Show unobtrusive progress and confirmed readiness, with actionable assistance when automatic connection or processing fails. Text/audio validation and durable acknowledgement follow the same contract as other senders. A bounded local sender outbox retains unacknowledged submissions for identical retry; accepted processing remains Server-owned.

Settings choose one CLI for LLM tasks. Each attempt pins the selection; changes affect subsequent attempts. Missing login/tools or quota failure never silently switches CLI or enables paid API execution. The status shows connection, selected-tool readiness, processing and last submission outcome. Database statistics are scoped Server API summaries of target and inbox/readiness counts, with freshness; no direct SQLite access. Practice stays in the Vue browser client. Personal profiles remain under the separately authorized external-agent API. Connection follows the [access boundary](architecture.md#private-release-and-recovery). Normal input and lesson presentation never expose raw JSON: show readable phrases, situations, help and reference-audio readiness. If prepared-file loading is offered, use understandable file selection with visible success or actionable empty/missing/invalid-input errors; loading/validation is distinct from confirmed publication.

Coach uses egui/eframe with the wgpu renderer (Metal on macOS, Direct3D 12 on Windows) and AccessKit for screen readers. Its compact drop/status/settings workflow does not require a second web frontend, and automated checks can drive the real views through the same accessible names a screen reader uses. VoiceOver and Narrator acceptance with the actual window remains a gate before the UI grows; the [remaining implementation plan](plan/implementation-plan.md#coach-desktop-workstream) tracks it. Views render snapshots and emit commands; a separate asynchronous runner owns API calls, leases, transfers and subprocesses. GUI dependencies belong only to Coach and never enter the Server build. Validate accessibility and native lifecycle behavior before expanding the UI.

The first release is a windowed application, with processing continuing while minimized. Normal launch automatically connects and enables bounded processing; a processing setting may pause it. Pausing stops new claims and lets the current job finish. Closing the window or choosing Quit stops claims, performs bounded worker cleanup and exits, leaving unfinished work recoverable through Server. There is no hidden tray worker, login startup, OS service or automatic updater in this scope. Multiple machines coordinate through Server leases; a second local instance must not start another runner for the same local configuration.

Connection loss shows the last confirmed status as stale. Sleep, restart, cancellation and ambiguous delivery must reconcile Server generations, leases and receipts before resuming; the UI never equates a successful subprocess exit with publication. Server owns budget accounting so restarting Coach or clearing its cache cannot reset daily starts. Local storage contains machine settings, bounded diagnostics, unacknowledged sender submissions and disposable processing staging/cache. Machine settings contain no application credentials; social sign-in storage will be decided with that later work. Provider CLI login remains under the adapter's documented authentication mechanism and out of ordinary job inputs.

## Inbox

**Item API.** A sender submits a phrase or word, explicit learning language, optional uploaded audio and optional free-text context specifying its sense or surrounding dialogue. Stable sender/item identities and submission revisions distinguish delivery retries from changed input. Optional source/group/turn references preserve lesson membership, dialogue order and speaker roles across submissions; explicit groups can be prepared together without batching unrelated entries. Attachment roles and exact text/language/provenance accompany audio. The same API serves echo-words and external import agents.

Coach supplies prompts, accepted variants, help and missing speech under the pinned [personal preferences](decision-personal-preferences.md). It does not invent an absent meaning. Source-faithful material with no defensible retrieval prompt may be study-only; unknown or ambiguous meaning fails with an actionable reason. An external agent or later learner note can supply missing context without an interactive question from the preparation job.

**Drop space.** A + button in the learning frontend opens a panel over the current screen for phrases, words or pasted text, with an optional learner note. It reads the clipboard only on a deliberate paste/input action, falling back to an empty box when unavailable. Deliberate paste/drop automatically starts the durable intake-to-publication workflow; opening or closing the panel alone transmits nothing. An optional note accompanies the input. Validate supported material visibly, preserve recoverable input and never silently lose it or create duplicate lessons on retry. A link in pasted text is data, not an instruction to import its page.

Closing the panel returns to the initiating card. Opening it during capture uses the existing interruption/release flow and retains recoverable bytes; it must not rebind or grade an attempt. Permission-pending, recording and comparison states need browser coverage. The panel shows recent delivery and preparation status without blocking practice when Coach is unavailable.

Frontend drops, recreation requests and external submissions use the same durable inbox in the core database. The API acknowledges receipt only after storing input and verifying attachment bytes. Waiting for Coach is distinct from successful preparation. Direct API senders retain their own outbox until that acknowledgement; after it, the core database owns processing failure and retry. Connectivity loss never loses accepted work or requires resending it with a new identity.

An entry preserves its original input. A changed note or explicit reprocessing request creates a new immutable generation, not an indistinguishable retry. Each generation pins input, preferences, guide version and existing target/revision bindings. Repeated delivery returns the existing receipt; conflicting payloads for the same identity are rejected. Recreation binds to its existing target and expected revision.

Status distinguishes waiting, preparing, failed with reason, pending core delivery and published results. Result counts distinguish ready-for-practice, study-only and awaiting-audio items. Counts come from committed receipts and readiness, never the agent's final message. Packages publish atomically; partial completion requires explicitly separate packages.

## Preparation jobs and permissions

Coach starts the selected Codex or Claude non-interactive CLI adapter, one entry or explicit group at a time. Support and verify both adapters on Windows and macOS; keep provider argument/output handling separate from process supervision. Subscription authentication, permissions and configuration are explicit. Never silently fall back to paid API credentials. No browser tools are needed or granted for inbox preparation.

An adapter authenticates only with the learner's CLI subscription login. Coach never supplies an API key, and where a CLI can refuse API-key login it is configured to, so a stored key fails the attempt instead of being billed. The adapter uses none of the learner's CLI customisation: user-level instructions, settings, MCP servers, connectors, hooks and plugins are excluded through the CLI's own options. Where a CLI cannot exclude user instructions through its own options, as Codex cannot for its home folder, Coach gives that CLI a separate home with its own subscription login, created by an explicit one-time setup login rather than by copying credentials.

File and network access is limited to the attempt. A CLI that can run commands is confined by an OS-enforced permission profile: it reads only the attempt, the platform runtime and the CLI's own installation, writes only inside the attempt and has no network. A broad sandbox mode is not enough, because it still lets commands read the whole disk and write shared temporary folders. A CLI without command execution gets only a file-reading tool, which the CLI itself confines to the attempt.

Each attempt gets a fresh working directory outside any repository, holding the staged inputs and the full prompt as a file, so no project instructions or version-control context load. The CLI receives only a short bootstrap naming that file, and its standard input stays closed: piped prompts are unreliable in both CLIs, which return empty output for long input or wait for an end of input that never comes, and a file avoids argument length and quoting limits. The CLI starts with an allowlisted environment rather than Coach's own, so a provider key, proxy or parent agent session exported in the learner's shell cannot change its authentication or behavior. The answer is read from the CLI's output: a successful exit with empty output is a failure, and neither progress text nor a zero exit code counts as a result.

The deterministic runner owns leases, generation fencing, bounded duration, attempt limits, output/media limits and a daily run budget. Authentication or quota failures stop repeated attempts until retry is appropriate. A late worker cannot publish after cancellation, lease replacement or a newer generation: accepting its result requires the current generation and fencing token. A crash after delivery recovers the publication receipt instead of generating new identities. Terminate worker subprocesses on cancellation where possible.

Ordinary jobs read the versioned preparation guide and a pinned preference snapshot and write only job outputs/staged media. They cannot alter active instructions, preferences, runner configuration, hooks or credentials, and cannot access learner recordings or unrelated files/accounts. Publication uses bounded job authority through the runner under the selected access boundary. Inbox material and API context remain data; only a direct learner note can give job-specific instructions, within these capabilities. Persistent preference changes use the separately authorized preferences API, not an import job.

Preparation performs bounded queries against existing target metadata for duplicates, preferred responses and confusables. Return only relevant candidates and no learner recordings; surface similarity never establishes identity. If the core API is unavailable, defer claims and result delivery rather than publish unchecked guesses. Jobs use their pinned preference revision; later preference changes never silently change a running job. Meaning compatibility and stable identities remain deterministic publication responsibilities.

## Preparation guide and provenance

The application-owned guide is versioned with the package format. It covers the [card rules](decision-targeted-drilling.md): fixed wording and slots, preferred expressions, distinct natural prompts, separated speaker turns, declared cross-target exposure, conservative familiarity marking with provenance, confusables across entries, comprehensible word contexts, accepted variants and help under the learner's preferences. Personal choices are database records, not edits to this guide. Ordinary preparation cannot promote its own working notes into governing instructions.

Every prepared package records its input generation, guide version, personal-preference revision and model/adapter identity where available. A bad preparation version can be located, suspended and reprocessed without rewriting history. Rollback of instructions alone does not repair already published cards. Changes to the guide are explicit maintenance work; external agents may update personal preferences through the authorized API on the learner's instruction.

## echo-words

echo-words exports new words to the inbox instead of Anki: the word, learning language, uploaded audio, chosen sense and source sentence, with stable identities. It keeps unsent entries in a durable outbox on its server and retries on new words and periodically. It removes only exact entries acknowledged by the inbox, so a word added during a send is not lost. Preparation failures remain visible after transport acknowledgement. Changes to echo-words require separate project authorization.

## Intake and preservation

The inbox API stores staged packages, media references and delivery state in the core database. The laptop may keep temporary output files for transfer retries, but accepted work and recovery state never depend on an independent laptop database. Core publication accepts stable submission IDs idempotently and rejects changed payloads under the same ID. Compatible revisions preserve target identity, history, recordings and unchanged chunk evidence; changed meanings create distinct targets. Source order and wording similarity are not identities. Pinned sessions retain their content, subject to lifecycle and stale-review exclusions.

Supplied reference audio requires verified uploaded bytes and exact text/language/role/provenance. Preserve course/actor originals. Reject supplied-but-untransferred or invalid audio rather than synthesizing a replacement. Neither service fetches arbitrary media URLs. Transfer hashes, durable receipts and reconciliation cover the boundary between inbox staging and core storage.

## Missing reference speech

Generate genuinely missing whole-phrase/turn audio in Coach before an item becomes practice-ready. Cache it and preserve exact speech input, engine/voice, locale/accent, settings and preparation version in its identity. Use one configured primary provider/voice per learning language and a fallback preserving language and intended locale/accent. Speech jobs have bounded leases/retries, synthesize outside database locks and recover without duplicate publication. An unavailable Coach or provider delays new audio, never playback of already published material.

Piper Lessac for US English, Piper Thorsten for German and Edge Sophie for Serbian are starting candidates, not a quality ranking. No macOS-only speech dependency. Serbian speech input may need Cyrillic conversion while displayed text stays unchanged; names, digraph boundaries and foreign words need checking. The Piper serbski_institut voice is Lower Sorbian and must not be selected as Serbian merely from its label. Supplied actor clips always take priority.

Actual speech listening and agent language quality remain distinct from schema/container tests. Choose voices using language-specific evidence. Private learner recordings stay in the core and are never preparation or provider inputs.

## Desktop architecture rationale

The read-only reference `../ibkr-porez-rs/` informed the egui/eframe toolkit, typed background results, egui_kittest interaction tests, native packaging and CI choices. Coach's Server-owned jobs and long-lived external processes require explicit cancellation, leases and recovery; the reference's tax workflow, file-backed authority, broad controller, automatic sync schedule, privileged CLI symlink installer and automatic release uploads do not apply. Dependency versions and release-signing acceptance are determined independently.
