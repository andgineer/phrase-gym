## 1. [P2] Preserve acknowledged exposure facts when an equal-version checkpoint arrives late

**Trigger:** Two tabs share a downloaded session. Tab A obtains a session response before a lookup exposure but receives it late. Tab B views that target in Library and reloads the session, retaining the new exposure fact. Tab A then processes its earlier response. No practice event or lifecycle transition occurred between the snapshots, so their sequence and version are identical.

**Expected:** An exposure fact already acknowledged and retained for this immutable session remains available to offline projection. A lookup in the closed five-minute window supports the original response even after a delayed read and reopening. R3/R4/R5 require retained evidence and server-compatible original-response chronology.

**Actual:** The older response overwrites the richer checkpoint, removing `support_exposures[target]`. Offline reopening and completion omit the first target's supported marker. Reconciliation changes that original response to `supported=true`; the server correctly retains the lookup. This is a local evidence/provisional-results bug, not a demonstrated incorrect authoritative schedule update.

**Verified ownership/line evidence:**

- `frontend/src/practiceJournal.ts:49–59` retains the current checkpoint only if its `last_sequence` or `version` is strictly greater. Equal counters permit unconditional replacement, including deletion of exposure facts.
- `src/phrase_gym/sessions/service.py:33–72` derives support facts from target-wide exposure history while session counters and `updated_at` remain session-owned. An external lookup legitimately changes this response without changing either counter; comparing `updated_at` alone would not solve this case.
- `frontend/src/composables/usePracticeSession.ts:115–124` displays the returned checkpoint, and lines 130–147 restore it offline.
- `frontend/src/offlineProjection.ts:35–37,60–65` derives and snapshots original support from those facts.

**Deterministic reproduction, independently executed in Chromium against the real built client/API/SQLite:**

1. Use `tests/browser_server.py` on a disposable port and a severable TCP proxy, with a fresh browser context. Set English UI, start an ordinary three-target session, and download it. Wait until the first `present` receipt is retained. Its original response is still null.
2. On tab A, intercept the exact `GET /api/v1/sessions/{id}`. Fetch the real response immediately, hold delivery behind a promise, then dispatch `online` to start restoration. Wait until the selected-session response is held. API requests were intercepted successfully in this Chromium reproduction; the disconnected transport later used the proxy, not page routing.
3. In tab B in the same context, navigate to `/learn/en/phrases/{first_target_id}`. Wait for the real exposure receipt to appear in the server's `support_exposures`, then navigate to the practice URL. Wait for enabled card controls and inspect IndexedDB `session:{id}`.
4. Release A's earlier response. After its controls enable, inspect the same IndexedDB entry. Observed: before and after both have `last_sequence=1`, `version=1`; the target's facts change from one acknowledged timestamp to `[]`.
5. Close A, sever the proxy, reload B, and rate all three targets Recalled within five minutes of the lookup. Its provisional results contain no supported marker. Restore the proxy and dispatch `online`; the first authoritative attempt has `original.supported=true`.

This reproduces erasure of information the device had already retained, rather than the unavoidable inability to know a disconnected device's new exposure. The existing delayed-read test covers a strictly greater sequence; it does not exercise external facts at equal counters. A WebKit attempt using page routes with a controlling worker did not reach the response gate, so the complete two-tab/offline reproduction is claimed for Chromium only.

**Correction direction:** Give append-only acknowledged facts a monotonic merge or an independently ordered snapshot contract. Preserve their target binding and actual occurrence times when retaining any session checkpoint, including equal-counter and rejected-older responses. Add this two-tab lookup → delayed read → offline completion → reconciliation regression; do not recompute already-created original responses.

## 2. [P2] Keep Stop recording available while session restoration is pending

**Trigger:** Native capture is active when an `online` signal starts session restoration, and the session read is delayed. This is reachable when connectivity returns during an offline take; a foreground/read retry can also overlap live media effects.

**Expected:** Restoration blocks starting new interactions while leaving cancellation and stopping available, as R5 explicitly specifies. Pressing Stop recording must end capture promptly and retain its bytes, without waiting for a server read.

**Actual:** The round Stop recording button becomes disabled while the synthetic microphone track remains live and the UI still says “Press again to stop recording.” Pause is also disabled. The learner must await the read or leave the view, which interrupts the take instead of allowing ordinary manual completion. A slow read therefore extends capture against the learner's intended stop.

**Verified ownership/line evidence:**

- `frontend/src/components/PracticePanel.vue:173–175` passes restoration/unavailability through the card's `ratingBusy` prop.
- `frontend/src/components/PracticeCard.vue:59–70` uses that prop to disable the shared microphone/stop/cancel button irrespective of its current action.
- `frontend/src/composables/usePracticeSession.ts:100–102,164–165` starts restoration on the online/foreground path; it does not stop the ongoing capture before disabling controls.

**Deterministic reproduction, independently executed in both Chromium and WebKit:**

1. Use the disposable browser server, block service workers for deterministic API instrumentation, and replace MediaDevices with an AudioContext oscillator/MediaStreamDestination as in `synthetic-capture.ts`. Retain native MediaRecorder, IndexedDB and Web Locks; silence playback. Do not request the operator's microphone.
2. Start ordinary practice and press Record. Wait for the enabled Stop recording button.
3. Route `GET /api/v1/sessions/current` through `route.fetch()`, holding delivery behind a promise. Dispatch `online`, then wait until the read is held.
4. Inspect the UI and synthetic track. Both engines returned `stopDisabled=true`, `trackState="live"`, `hintVisible=true`, `pauseDisabled=true`.
5. Release the response. Stop recording becomes enabled again and can finish the take.

The existing held-read regression checks introduction/detour/download admission. The combined capture regression interrupts on navigation; neither checks manual stopping while restoration holds the current view.

**Correction direction:** Distinguish admission of a new recording from control of an already-active recording, permission request or playback. Keep resource stop/cancel available during restoration while retaining new-action guards and terminal evidence cleanup. Add a held-read regression with live capture; cover cancellation and playback stopping through the same ownership rule.

## 3. [P2] Revalidate the complete shell before claiming an existing pack is offline-ready

**Trigger:** A verified download's shell JavaScript entry is evicted from CacheStorage while its selected media and IndexedDB pack remain. A connected reload obtains that script from the network, so the app can still inspect the pack before the learner disconnects.

**Expected:** Existing-pack readiness verifies the complete shell as well as media, per R6. The app should show recovery/redownload guidance or repair the shell while connected before promising offline reopening.

**Actual:** A connected reload still shows “Verified for offline practice.” In WebKit, severing the origin and reopening then produces an empty page: the cached HTML survives, but the required JavaScript cannot be fetched. No app-level recovery guidance can render. This is not unavoidable eviction after a successful verification: the missing shell entry already existed before the connected reload's readiness check.

**Verified ownership/line evidence:**

- `frontend/src/sessionPack.ts:18–48` verifies compatibility and selected-media bytes/hash, but never calls `verifyOfflineShell` before returning a ready pack.
- `frontend/src/sessionPack.ts:54` verifies/repairs the shell only during an explicit new download.
- `frontend/src/composables/useSessionPack.ts:12–25` turns an existing `verifyPack` result into the readiness badge.
- `frontend/public/sw.js:43–46` serves cached HTML and falls back to network for the missing asset. A connected asset fetch does not repopulate the shell cache.

**Deterministic reproduction, independently executed against a real worker and severable TCP proxy:**

1. Start/download an ordinary session and wait for its readiness badge and controlling worker.
2. Remove only the built JavaScript entry from the `phrase-gym.shell.*` cache:

   ```javascript
   const name = (await caches.keys()).find(n => n.startsWith('phrase-gym.shell.'))
   const cache = await caches.open(name)
   const entry = (await cache.keys()).find(r => r.url.endsWith('.js'))
   await cache.delete(entry)
   ```

3. Reload while connected. Both engines still showed the readiness badge (`count=1`). The deleted entry was `/assets/index-1tZ5xpst.js` in the reviewed build.
4. Sever the disposable proxy and reload without a second Download action. WebKit returned zero `.practice-panel` elements and an empty body. Chromium's HTTP cache masked the missing shell asset in this run and still rendered; this is not claimed as a Chromium reopen failure.

The existing evicted-shell test explicitly downloads again, which repairs the shell. It does not establish existing-pack readiness after eviction without that action.

**Correction direction:** Include complete-shell verification in restored readiness and offline admission, and clear the badge with actionable guidance when verification fails. Repair while connected if appropriate. Add eviction → connected restore/readiness → disconnected reopen coverage without an intervening download; distinguish browser HTTP-cache fallback from a complete verified worker shell.
